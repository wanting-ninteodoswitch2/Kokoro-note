# ま。Guard v0.5

対象アプリを開こうとしたときに一時停止画面を挟み、使いすぎに気づかせるAndroidアプリ。

## v0.5での追加

### 摩擦（ひと手間）— アプリごとにオンオフ可能

待ち時間だけの介入は、慣れると無意識に待てるようになります。
カウントダウンを待ってタップする動作自体がルーティン化してしまう。
そこで「開く」判断に意識を戻すためのひと手間を選べるようにしました。

| モード | 内容 | 強さ |
|---|---|---|
| なし | タップするだけ | － |
| 長押し（3秒） | 押し続ける。進捗バーで残りが見える | 弱 |
| 理由を書く | なぜ開くのかを一言入力。記録が残る | 中 |
| 文章を書き写す | 指定文を正確に入力しないと開けない | 強 |

**「理由を書く」の記録が振り返れます。** メイン画面の「開いた理由」から
直近50件を確認でき、自分がどんなときに開いているかのパターンが見えます。

**書き写しモードはコピペ回避対策済み。** テキスト選択メニューを無効化してあります。
書き写す文章は自由に設定できます（初期値：「これを見ることは、いま本当に必要ではない。」）

### ホーム画面ウィジェット

オーバーレイの介入は「開こうとした後」——手が動いてしまった後にしか働きません。
ウィジェットは**開く前**、ホーム画面を見た瞬間に数字が目に入ります。

表示内容：
- 今日の対象アプリ合計使用時間
- 今日の起動回数
- 上限に対する進捗バー
- 今日やめられた回数・連続日数

介入が起きるたびに自動更新されます。

## 機能全体

### 3つの介入タイミング
1. **起動時** … 開いた瞬間に一時停止画面
2. **連続使用の超過** … n分続けて見ていたら「まだ、続ける？」
3. **1日の上限到達** … 合計時間・起動回数が上限を超えたら「見る」を出さない

### 実測ベースの計測
`UsageStatsManager` でOSの利用ログを読み、`AlarmManager` の
`setExactAndAllowWhileIdle` でDoze中でも確実に発火します。
アプリを行き来しても累積が正しく積み上がります。

### 時間帯ルール
「朝6〜8時は開かない」「夜22時以降は30秒待つ」など。プリセットあり。

### 7日間グラフ
やめた/見た回数の積み上げ棒グラフ（自作View）。

## セットアップ

### 1. Android Studio
https://developer.android.com/studio （PC / Mac が必要）
「Open」→ このフォルダを選択。

### 2. 実機にインストール
1. 設定 → デバイス情報 →「ビルド番号」を7回タップ
2. 開発者向けオプション →「USBデバッグ」をON
3. USB接続 → 実行ボタン（▶）

### 3. 4つの権限
| 権限 | 必須 | ないとどうなるか |
|---|---|---|
| 1. アプリ検知（アクセシビリティ） | 必須 | 何も起きない |
| 2. 重ねて表示 | 必須 | 一時停止画面が出ない |
| 3. 使用状況へのアクセス | 必須 | 実測できず、再確認・上限・ウィジェットが働かない |
| 4. 電池最適化を除外 | 強く推奨 | 数時間後に検知が止まる |

### 4. ウィジェットの設置
ホーム画面を長押し →「ウィジェット」→「ま。Guard」を選んで配置。

## 構成

```
MaAccessibilityService   前面アプリの検知と介入判断（中核）
  ├─ UsageTracker        UsageStatsManagerで実測値を取得
  ├─ UsageAlarmScheduler AlarmManagerで再確認を予約
  └─ OverlayService      一時停止画面の表示（3モード）
       └─ FrictionController  長押し/理由入力/書き写しの制御

UsageWidgetProvider      ホーム画面ウィジェット
Prefs                    設定・時間帯ルール・統計・理由履歴の永続化
MainActivity             権限セットアップ・統計・アプリ選択・摩擦設定
TimeRulesActivity        時間帯ルールの管理
WeeklyChartView          7日間グラフ（Canvas描画）
```

画面の中身は読み取っていません。`canRetrieveWindowContent="false"` を設定しており、
参照するのはパッケージ名と、OSが提供する利用時間の統計のみです。

## v0.5.1 デバッグ修正

コードレビューで見つかった不具合を修正しました。

### 実機で必ず問題になっていたもの

**1. ウィジェットが一覧に出ない**
`UsageWidgetProvider` の `exported="false"` が原因。ウィジェットのレシーバーは
システムから `APPWIDGET_UPDATE` を受け取るため `exported="true"` が必須。

**2. アラーム経由の再確認が例外で落ちる**
Android 8以降、バックグラウンドから `startService` は
`IllegalStateException` になる。`OverlayService` をフォアグラウンドサービス化し、
`startForegroundService` で起動するよう変更。通知は `IMPORTANCE_MIN` で
音もバナーも出ない最小構成にしている。

**3. 書き写しモードで文字が入力できない**
`EditText.setTextIsSelectable(false)` は内部で `focusable` と `clickable` を
falseにするため、編集不能になっていた。長押し無効化＋
`customInsertionActionModeCallback` による貼り付け封じに置き換え。

### 使っていて気づきにくいが確実にあったもの

**4. 長押しが途中で解除されることがある**
`ValueAnimator.cancel()` でも `onAnimationEnd` が呼ばれる仕様のため、
進捗値だけで判定していると誤解除が起きる。明示的なフラグで区別するよう修正。

**5. 戻るキーで閉じられない**
キーボード入力のためフォーカスを受け取るウィンドウにした結果、
戻るキーが効かず閉じられなくなっていた。戻る＝「やめておく」として処理を追加。

**6. キーボードが残る**
理由入力後にオーバーレイを消してもソフトキーボードが残ることがあったため、
明示的に閉じる処理を追加。

### 品質面

**7. 画面切り替えのたびに1日分のログを走査していた**
端末によっては表示がもたつくため、10秒間のキャッシュを追加。

**8. 初期化順序の潜在的なクラッシュ**
`lateinit` を `by lazy` に変更。

**9. グラフの文字サイズが端末解像度で変わる**
px指定を density を掛けたdp相当に修正。

**10. 再起動後の処理を実装**
`BootReceiver` を追加（ウィジェットの更新）。アクセシビリティサービス自体は
OSが自動的に再開するため、ユーザーの再設定は不要。

## v0.5.2 2回目のレビューで見つかった不具合

前回のレビューでは実行時クラッシュに繋がるものを優先しましたが、
今回はコードを1行ずつ読み直し、正しく動くが「間違った結果を返す」種類の
不具合と、UI上で操作できなくなる不具合を中心に見つけました。

### 複数の対象アプリを使っていると起きるもの

**11. アラームの取り違え**
`UsageAlarmScheduler` の `PendingIntent` が全パッケージで同じ requestCode
（固定値1001）を使っていました。`PendingIntent` の同一性は component /
action だけで決まり extras は見ないため、アプリAの再確認を予約した直後に
アプリBの再確認を予約すると、内部的には「同じ」アラームとして扱われ、
Aの予約がBの内容で上書きされてしまいます。`cancel(A)` を呼んだつもりが
実際にはBの予約を消してしまう、ということも起こり得ました。
`packageName.hashCode()` を requestCode に使うよう修正し、
アプリごとに独立したアラーム枠を持つようにしました。

### 実際の使い方で機能が働かなくなっていたもの

**12. 通知バーを開くだけで連続使用のカウントがリセットされる**
`getCurrentSessionMinutes` は `MOVE_TO_BACKGROUND` が記録されるたびに
セッションを0にリセットしていました。しかし通知バーを一瞬開く、
着信を確認する、といった動作でもこのイベントが記録されることがあり、
これでは「n分続けて見たら再確認」がほとんど発動しません。
90秒以内に前面へ戻った場合は同じセッションの続きとして扱うよう変更しました。

**13. 同じ理由で起動回数が水増しされる**
`getTodayLaunchCount` も同様に、一瞬の中断のたびに「1回」と
カウントしていました。「1日◯回まで」の上限が実態より早く
発動してしまうため、同じ90秒の許容時間を適用しました。

### UIで操作できなくなっていたもの

**14. アプリ設定ダイアログが画面からはみ出す**
待ち時間・猶予・連続使用・1日の上限・摩擦設定と項目が増えたにもかかわらず
`ScrollView` で囲んでいなかったため、画面の小さい端末では下部
（摩擦の種類の選択、書き写す文章の入力）が画面からはみ出し、
操作できなくなっていました。`dialog_time_rule.xml` では
最初から対応できていたのに、こちらは見落としていました。

### 品質・将来のOS対応

**15. 一覧のON/OFF切り替えでウィジェットが更新されない**
アプリ設定ダイアログの保存時はウィジェットを更新していましたが、
一覧をタップして対象アプリを追加/削除したときは更新していませんでした。

**16. Android 14以降でのフォアグラウンドサービス型の明示**
マニフェストに `foregroundServiceType="specialUse"` を書いていましたが、
Android 14以降はコード側の `startForeground()` 呼び出しでも型を
明示するのが推奨されているため対応しました。

## 既知の限界（バグではなく設計上の制約）

- `UsageStatsManager` の記録には数秒〜数十秒のラグがあり得るため、
  1日の起動回数上限は「上限ちょうど」のタイミングで多少前後することがあります
- 通知の表示には Android 13+ で `POST_NOTIFICATIONS` の実行時許可が要りますが、
  このアプリの通知は意図的に最小重要度で目立たないものなので、
  許可がなくても機能自体（オーバーレイ表示）は問題なく動きます

## v0.5.3 セカンドオピニオン（Gemini）を受けての対応

外部のAIレビューを受け、指摘を1件ずつ実コードと突き合わせて検証しました。
**12件の指摘のうち、採用が4件、既に対応済みが2件、事実誤認が6件**でした。

### 採用した指摘（本物の不具合）

**17. `unsafeCheckOpNoThrow` が API 29 追加なのに無防備だった**
minSdk 26 なので、Android 8.0 / 8.1 / 9 で `NoSuchMethodError` になります。
これは自分のレビューで見落としていた本物のバグでした。
API 29 未満では非推奨の `checkOpNoThrow` にフォールバックするよう修正。

**18. アラームIDの採番方法（設計論点C）**
`packageName.hashCode()` は 32bit のため衝突の可能性がゼロではなく、
衝突すると別アプリのアラームを取り違えます。
`Prefs` 側で連番IDを採番・永続化する方式に変更しました。

**19. `ACTIVITY_RESUMED` / `ACTIVITY_PAUSED` の採用（設計論点A）**
`MOVE_TO_FOREGROUND` / `MOVE_TO_BACKGROUND` は API 29 で非推奨になり、
マルチウィンドウやメーカー独自ROMでの取りこぼしが報告されています。
API 29 以降は新しいイベントを使うよう分岐を追加しました。
なお 90秒の閾値については「妥当」との評価だったので維持します。

**20. ウィジェットの旧端末向けフォールバック**
`minResizeWidth` / `minResizeHeight` を併記して補強しました。

### 既に対応済みだったもの

- **`canScheduleExactAlarms()` の確認**：v0.4 の時点で分岐と try-catch の
  二重で対応済み
- **マニフェストのネストクラス記述**：`$` 区切りで正しく記述済み
  （Geminiの推奨形式と一致）

### 事実誤認だった指摘（修正すると壊れるため不採用）

以下は実際のコードには存在しない、あるいは既に正しい記述でした。
**AIのレビューも間違えるという実例として残しておきます。**

| 指摘内容 | 実際 |
|---|---|
| `UsageAlarmScheduler.kt` 70行目のインスタンス化構文エラー | 70行目は `buildPendingIntent` のコメント。`UsageAlarmReceiver::class.java` と正しく記述済み |
| `OverlayService.kt` の `view.postDelayed` / `Handler.post` で `this` 解決エラー | このファイルに `postDelayed` も `Handler` も存在しない |
| `TimeRulesActivity.kt` のミリ秒計算の型不一致 | このファイルにミリ秒計算は存在しない |
| `TimeRulesActivity` から `WeeklyChartView` への値渡しで型不一致 | 両者に参照関係はない |
| `WeeklyChartView.kt` の `drawRect` に Int を渡している | 全座標が `Float` 由来（`density`、`toFloat()`、`0.4f` 等） |
| `startForeground` 3引数版を API 29 でガードすべき | 3引数版自体は API 29 だが、渡す定数 `FOREGROUND_SERVICE_TYPE_SPECIAL_USE` と マニフェストの `specialUse` が API 34 追加のため、34 ガードが正しい |

### 保留にした提案

**オーバーレイ上のキーボード入力を、透明Activityに移す（設計論点B）**

「カスタムROMでIMEが不安定になるリスクが高い」という指摘自体は妥当だと
考えていますが、透明Activityへの移行は
「対象アプリの上に被せる」という現在の体験（画面遷移が起きない滑らかさ）を
損なう可能性があります。

まず実機で現在の実装を試し、実際にキーボードが不安定なら移行する、
という順序で判断します。ここは机上で決めるより実機の挙動を見るべき部分です。

## v0.5.4 2回目のセカンドオピニオンへの対応

### 有効だった新規指摘

**21. `addView` 前にオーバーレイ権限を確認していない**
オーバーレイ権限はユーザーが設定画面で後から取り消せます。
取り消された状態で `WindowManager.addView()` を呼ぶと
`BadTokenException` でクラッシュするため、表示直前の確認を追加しました。

あわせて、メーカー独自ROMの制限で `addView` 自体が失敗する場合にも
備えて try-catch で保護しています。ここで落ちると、
対象アプリの通常利用まで巻き添えにしてしまうためです。

### 注意：このレビューは古いバージョンに対して行われた可能性が高い

2回目のレビュー内容は、1回目とほぼ同一でした。具体的には：

**v0.5.3 で修正済みの項目が、未修正として再度指摘されている**
- `unsafeCheckOpNoThrow` の API 分岐 → 対応済み
- `hashCode()` ではなく連番IDを使う → 対応済み
- `ACTIVITY_RESUMED` の採用 → 対応済み
- ウィジェットの `minWidth` / `minHeight` 併記 → 元から記述あり
- `canScheduleExactAlarms()` の確認 → v0.4 から対応済み
- 全レシーバーの `exported` 明示 → 元から全て明示済み

**1回目と同じ事実誤認が、そのまま繰り返されている**
- `UsageAlarmScheduler.kt` 70行目のネストクラス参照エラー
- `OverlayService.kt` の `view.postDelayed` / `Handler` での `this` 解決
- `WeeklyChartView.kt` の `drawRect` に Int を渡している
- `TimeRulesActivity.kt` の Int / Long 演算不一致

これらは1回目のレビュー時に実コードと突き合わせて確認済みで、
該当するコードがそもそも存在しません（`postDelayed` も `Handler` も
`OverlayService.kt` には無く、`WeeklyChartView` の座標は全て Float 由来）。

同じ誤りが2回続けて出ている以上、指摘内容ではなく
**レビューに渡したコードが古かった可能性**を疑うべきです。
再度依頼する場合は v0.5.4 の zip を渡してください。

### 判断を変えなかった点

`startForeground` を API 29 でガードすべきという指摘は今回も出ましたが、
渡す定数 `FOREGROUND_SERVICE_TYPE_SPECIAL_USE` 自体が API 34 追加であり、
マニフェストの `specialUse` も API 34 以降でしか有効になりません。
API 29 でガードすると Android 10〜13 で不正な型を渡すことになるため、
34 ガードのままとします。

## v0.6.0 3回目のレビュー（ChatGPT）への対応

このレビューは実際にコードを読んだ上での指摘で、
**アプリの中核機能が設定通りに動いていない致命的なバグ**が見つかりました。

### 最重要：`usageLimitMin` が機能していなかった

**症状**: 「15分で再確認」と設定しても、猶予（5分）が経過した時点で介入していた。

**原因**: 2つの意味の違う「分」を取り違えていました。

| 設定値 | 本来の意味 |
|---|---|
| `graceMinutes` | 「見る」直後に、起動時の介入を抑える時間 |
| `usageLimitMin` | これだけ続けて使ったら声をかける時間 |

`unlockAndOpen()` が `graceMinutes` でアラームを予約しており、
さらに `UsageAlarmReceiver` 側でも実測セッションと `usageLimitMin` を
照合していなかったため、猶予が切れた瞬間に介入していました。

**修正**: アラームに「何分後に鳴らすか」だけでなく
「セッションが何分に達したら介入するか（threshold）」を持たせ、
受信側で実測値と照合するようにしました。閾値に達していなければ
残り時間で予約し直すので、設定した時間が必ず守られます。

```
0分:  開く → 「見る」→ 猶予5分 / アラームを15分後・閾値15分で予約
15分: アラーム発火 → セッション15分 ≧ 閾値15分 → 介入   ← 設定通り
```

### その他の採用した指摘

**23. 猶予がメモリ上にしかなかった**
`graceUntil` が `mutableMapOf` だったため、OSにプロセスを落とされると
猶予が消え、アプリに戻った瞬間にまた介入が出ていました。
バックグラウンドのサービスは普通に落とされるので、Prefs に永続化しました。

**24. 統計キャッシュがアプリ切り替えで効かない**
「直近1件」だけを保持する `Pair` だったため、アプリAとBを行き来すると
毎回キャッシュが捨てられ、ほとんど機能していませんでした。
パッケージ単位の `Map` に変更しています。

**25. アラームID採番の競合**
`AccessibilityService` / `BroadcastReceiver` / UI の複数経路から
呼ばれるため、`@Synchronized` で直列化しました。

**26. 時間帯ルールの 00:00〜00:00 が「該当なし」になる**
`until` で扱っていたため、終日のつもりで設定すると何も起きませんでした。
開始と終了が同じ場合は「終日」と解釈し、表示も「終日」と出すようにしました。

**27. コピペ対策の説明が実態より強かった**
長押しメニューを封じているだけで、IMEの履歴など他経路は塞げません。
「無意識のコピペを防ぐ程度」であることをコメントに明記しました。
この機能の目的は不正防止ではなく気づきを促すことなので、実装は現状のままです。

**28. 「連続して見ています」という表現が不正確**
90秒以内の中断は同じセッションとして数えているため、
「◯分、見ています」という表現に変更しました。

### 検討した上で変更しなかった点

**`dailyLaunchLimit` の `>` と `>=`**

「`>` は off-by-one では」という指摘ですが、`todayLaunches` には
今まさに開いた回も含まれるため、10回設定なら11回目に `11 > 10` が成立して
止まります。`>=` にすると10回目で止まり、「10回まで」の設定なのに
9回しか開けなくなります。現状の `>` が正しいと判断しました。

ただし UsageStats の記録には僅かなラグがあり、今回の起動がまだ
記録されていないと1回分ずれる可能性はあります。厳密な回数管理ではなく
目安として扱う旨をコメントに明記しました。
UI の説明文も「上限を超えると」に修正しています。

### 今後の課題として受け止めた点

- Android 15 以降ではバックグラウンドからのFGS起動条件がさらに厳しくなり、

## v0.6.1 4回目のレビューへの対応

### 最重要：6時間ルックバックの穴（このアプリの存在意義に関わる問題）

**症状**: 同じアプリを6時間以上ぶっ通しで使うと、介入が一切来ない。

**原因**: `getCurrentSessionMinutes()` が直近6時間分のイベントしか見ていなかったため、
それより前に始まったセッションは開始点が窓の外に出てしまい、
「開始点が見つからない＝使っていない」と誤判定して 0 を返していました。

`UsageAlarmReceiver` は 0 を「すでに離れている」と解釈するため、
**このアプリが最も介入すべき長時間利用者に対して、何もしない**という
本末転倒な状態になっていました。

**修正**: 2段構えで対処しました。

1. ルックバックを24時間に拡張（日をまたぐセッションもカバー）
2. `isCurrentlyForeground()` を新設し、セッション時間の計算とは
   独立して「いま前面にいるか」を判定できるようにした

そのうえで、開始点が見つからなくても現在前面にいる場合は
「少なくとも窓の長さだけは使っている」とみなします。
`UsageAlarmReceiver` 側も「セッション0＝離脱」という決めつけをやめ、
前面判定で確認してから介入を判断するよう変更しました。

### 起動回数上限を「目安」から「確定値」へ

**指摘**: `UsageStats` の反映遅延次第で境界が甘くなる。

これは前回「厳密な回数管理ではなく目安」とコメントで逃げていた部分ですが、
構造自体を変えて解決しました。

**変更**: アクセシビリティサービスは起動を即座に検知できるので、
その時点で自前カウントを記録するようにしました（`Prefs.recordLaunch`）。
判定にはこの自前カウントと `UsageStats` の値の大きい方を使います。

- 自前カウント … いま開いた回まで確実に含む（境界が正確）
- UsageStats  … アプリを止めていた間の起動も拾える

90秒以内の再前面化は同じ起動の続きとみなすため、
通知バーを覗くような往復で回数が水増しされることもありません。

ロジックはシミュレーションで検証済みで、
「10回まで」の設定に対してちょうど10回開け、11回目でブロックされます。

なおこの実装中に、初回起動が0回とカウントされる
オフバイワンのバグを自分で作り込んでいたのを検証で発見し、修正しました。
（`lastAt` の未設定と「前回が古い」を区別していなかったため）

### 今後の課題

- Android 15 以降のFGS起動条件（target 35 以降では
  `SYSTEM_ALERT_WINDOW` の例外に「現在表示中のオーバーレイ」が必要）
- Google Play 公開時の `QUERY_ALL_PACKAGES` とアクセシビリティの用途申告

## v0.6.2 5回目のレビューへの対応

### 指摘1：フォールバック条件（採用、ただし原因はもっと深かった）

**指摘**: `!sawAnyEvent` が条件に入っているため、前面/背面以外のイベントが
1件でもあるとフォールバックが働かない。

これは正しい指摘で、そのとおり削除しました。`sessionStartedAt == 0` は
すでに「窓の中に前面イベントが無い」ことを意味しているので、
追加の条件は不要でした。

**ただし、これを直しただけでは問題は解決しませんでした。**

フォールバックの判定に使っている `isCurrentlyForeground()` 自体が、
直近10分しか遡っていませんでした。前面イベントは「切り替わった瞬間」にしか
記録されないため、10分以上ずっと同じアプリを見ていると、
その窓には前面イベントが1件も存在しません。結果、
救済役であるはずの関数が `false` を返し、`!sawAnyEvent` を外しても
フォールバックは依然として発動しないままでした。

**修正**: 窓を段階的に広げる方式にしました。
まず短い窓（10分）で探し、前面イベントが1件も見つからなければ
「誰かがずっと前面にいる」と判断して24時間の窓で再確認します。
通常のアプリ切り替えは短い窓で解決するので、
重い24時間走査は長時間セッションのときだけに限定できます。

### 指摘2：ホーム画面経由で起動回数を取りこぼす（不採用）

検証したところ、この指摘は成立しませんでした。

除外しているのは `com.android.systemui` だけで、
ホーム画面（ランチャー）は別パッケージです。
そのため `アプリ → ホーム → アプリ` では `previous` がランチャーになり、
`recordLaunch()` は正しく呼ばれます。

`systemui` を除外しているのは、通知バーを一瞬覗いただけで
起動回数が水増しされるのを防ぐための意図的な設計です。
誤ってバグと判断されないよう、コメントに意図を明記しました。

### 指摘3：UsageStats の反映遅延（Android仕様上の限界として受容）

1日の使用時間上限について、境界付近で数分のずれが出る可能性は残ります。
起動回数については自前カウントで解決しましたが、
使用時間まで自前で積算すると、アクセシビリティサービスが
止まっている間の時間を取りこぼすという別の不正確さが生じます。
現状は UsageStats を信頼する方が総合的に正確と判断しました。

### テストを追加

`app/src/test/java/com/uma/maguard/SessionLogicTest.kt` を追加しました。
`UsageStatsManager` 本体はOSに依存して単体テストできないため、
判定ロジックを純粋な計算として切り出し、イベント列を与えて検証しています。

過去に実際バグが出た箇所を回帰テストとして重点的に押さえました。

## v0.7.2 オーバーレイの状態管理を修正

引用付きの外部レビューで、**上限を回避できる抜け道**が見つかりました。
これまで6回のレビューで一度も指摘されなかった種類の問題です。

### 🔴 別アプリのオーバーレイに答えて、目の前のアプリが素通しになる

**再現手順**

1. Instagram（対象）を開く → オーバーレイAが表示される
2. 履歴（最近使ったアプリ）から X（対象）に切り替える
3. Xの検知は走るが、`OverlayService` は
   `if (overlayView != null) return` で要求を無視する
4. 画面に残っているオーバーレイAで「見る」を押す

**結果**: 猶予が付くのは Instagram。しかし実際に手元にあるのは X で、
Xは何の介入も受けずに使えてしまいます。

上限を設定したのに開けてしまうのは、このアプリにとって
最も避けたい失敗です。

**修正**: 表示中と異なるパッケージの要求が来たら、
現在のオーバーレイを外して出し直すようにしました。
同じアプリの場合のみ、これまで通り無視します。

差し替え用に「ビューだけ外す」処理を分離しています。
`removeOverlay()` は `stopSelf()` まで呼ぶため、
直後の表示要求が停止処理と競合して表示されないことがあるためです。

### 🔴 対象外アプリに移るとオーバーレイが残り続ける

`config == null`（ホーム画面や設定など対象外のアプリ）のとき、
単に `return` していたため、直前のオーバーレイが画面に残り、
**戻るキーを押すまで関係のないアプリの操作まで妨害**していました。

`OverlayService.dismiss()` を追加し、対象から外れた時点で
表示を畳むようにしました。

### 🟠 全部やめられた日だけ、グラフの棒が底辺を突き抜ける

`WeeklyChartView` で、やめた回数の矩形の下端に `corner` を
足していました。これは下側の角丸をグレーの矩形に隠して
「上だけ角丸」に見せるための処理です。

しかし見た回数が0の日はグレーの矩形が存在しないため、
そのまま足すと底辺を約4px突き抜け、日付ラベルに重なります。
**一番良い日ほど表示が崩れる**という状態でした。

見た回数が0の場合は `corner` を足さないよう修正しました。

### 状態遷移の検証

差し替えロジックを4つのシナリオでシミュレーション検証済みです。

| シナリオ | 期待 | 結果 |
|---|---|---|
| 履歴から別の対象アプリへ | オーバーレイが差し替わる | ✅ |
| 同じアプリ内で画面遷移 | 二重表示しない | ✅ |
| 対象外アプリへ移動 | オーバーレイが消える | ✅ |
| 対象外を経由して別の対象へ | 新しい方が表示される | ✅ |

## v0.7.3 閉じる処理からサービス起動をなくした

### 🔴 日常操作のたびにサービス起動要求が飛んでいた

v0.7.2 で追加した `OverlayService.dismiss()` は、内部で
`startForegroundService` を呼んでいました。

この関数は「対象外アプリに移った」ときに呼ばれます。つまり
**ホーム画面・設定・LINE といった日常操作のたびに、
オーバーレイが出ていない平常時ですら、毎回サービス起動要求が
飛んでいた**ことになります。

`SYSTEM_ALERT_WINDOW` を持つアプリはバックグラウンド起動制限の
例外扱いになるため即座にクラッシュするとは限りませんが、

- 無駄なサービス起動と通知のちらつき
- 電池消費
- Android 15 以降で例外条件がさらに厳しくなる見込み

を考えると、依存すべき実装ではありませんでした。

**修正**: そもそも「閉じる」のに新しくサービスを起動する必要はありません。
動作中のインスタンスへの参照を `companion object` に持たせ、
直接伝える方式に変更しました。動いていなければ何もしません。

```kotlin
fun dismiss(stillForeground: Boolean = false) {
    if (stillForeground) return
    val service = instance ?: return
    if (service.overlayView == null) return
    Handler(Looper.getMainLooper()).post { service.removeOverlay() }
}
```

呼び出し側にも `if (OverlayService.isShowing)` のガードを入れ、
二重に無駄な処理を防いでいます。

これで `startForegroundService` の呼び出しは、
実際にオーバーレイを表示する2箇所だけになりました。

### 🟠 画面分割で介入をすり抜けられる可能性への対処

「上に対象アプリ、下に対象外アプリを開き、下をタップすると
オーバーレイが消えて上の対象アプリを使えてしまうのでは」
という指摘がありました。

検証したところ、オーバーレイは全画面かつタッチを独占する設定
（`FLAG_NOT_TOUCHABLE` を付けていない）なので、
表示中に下のペインを触ること自体ができません。
そのため指摘のシナリオはそのままでは成立しません。

ただし通知経由など、タッチ以外で別アプリが前面に来る経路は残ります。
念のため、閉じる前に対象アプリがまだ前面扱いかを確認し、
残っている場合はオーバーレイを維持するようにしました。

### レビューが読めていなかった件について

今回のレビューは、渡した zip がバイナリとして展開されてしまい、
**コード全体が読めない状態で行われた**ものでした。
指摘は依頼文に載せたスニペットのみを根拠にしています。

それでも今回の指摘が有効だったのは、こちらが事前に
「この実装で問題ないか」と具体的に懸念を書いていたためです。
懸念を明示しておくと、部分的な情報しか渡らなくても
的確な検証が得られる、という点は今後にも活かせます。

## v0.7.4 並行性とパフォーマンスの修正

全ソースを読んだ外部レビューで、正しく見える実装が実際には
機能していない箇所が見つかりました。

### 🔴 `@Synchronized` が排他制御として機能していなかった

`Prefs.getAlarmId()` と `recordLaunch()` に `@Synchronized` を
付けていましたが、**ロックとして働いていませんでした。**

`Prefs` はシングルトンではなく、呼び出しのたびに
`Prefs(context)` と new されています。インスタンスメソッドへの
`@Synchronized` は「そのインスタンス」に対するロックなので、
別インスタンスから同時に呼ばれた場合はすり抜けます。

アクセシビリティサービス・アラーム受信機・UI という
複数経路から呼ばれる設計なので、実際に競合し得る状態でした。
アラームIDが重複すれば、別アプリのアラームを取り違えます。

**修正**: ロックを `companion object` に置き、
全インスタンスで同じ錠前を使うようにしました。
書き込みを伴う処理はすべてこのロック下に入れています。

### 🔴 画面が切り替わるたびにJSONをパースしていた

`onAccessibilityEvent` は画面のウィンドウ状態が変わるたびに
**メインスレッドで**呼ばれます。その中の
`getEffectiveConfig()` は内部で `getTargets()` を呼び、
毎回 SharedPreferences から長いJSON文字列を読んでパースしていました。

対象アプリが増えるほど重くなり、端末全体の操作の
もたつきにつながる実装でした。

**修正**: パース済みの設定をメモリに保持し、
保存時にキャッシュを更新する方式にしました。
書き込みは必ず `saveTargets` / `saveTimeRules` を通るので、
実データとずれることはありません。

### 🔴 ウィジェット更新でANRの可能性

`AppWidgetProvider.onUpdate()` もメインスレッドで実行されます。
その中で対象アプリごとに `UsageStatsManager` へ問い合わせ、
最大24時間分のイベントを走査していました。

**修正**: `goAsync()` でブロードキャストの寿命を延ばし、
別スレッドで集計してから表示を更新するようにしました。
処理を「重い集計（`collectSnapshot`）」と
「軽い表示変換（`buildViews`）」に分けています。

### 判断を変えなかった点

**サービスの静的参照について**

アンチパターンだという指摘はその通りですが、問題になるのは主に
Activity の場合です。View階層とウィンドウを抱えたまま残るためで、
Service はそれらを保持しません。
`onCreate` で設定し `onDestroy` で null にしており、
プロセス終了時は静的変数も一緒に消えます。

状態だけを別クラスに持たせる案も検討しましたが、
「閉じる」には結局サービス本体を呼ぶ必要があり、
参照の置き場所が変わるだけで実質は同じです。
層を増やして意図が分かりにくくなる方が損だと判断しました。

**`isCurrentlyForeground` を `queryUsageStats` に置き換える案**

`lastTimeUsed` を見る方式は高速ですが、
「最後に前面に来たのがどのアプリか」の判定精度が落ちます。
このアプリでは、この判定が
「長時間セッションを取りこぼさないための最後の砦」になっているため、
速度より正確さを優先します。
呼び出し頻度も、短い窓で解決しない場合に限定済みです。

### 補足：バージョン番号の不一致について

レビューで指摘された `versionName = "0.7.2"` は、
ソースをテキスト化した直後にバージョンを更新したため、
**渡したファイルだけが古かった**ものです。
リポジトリ側は当時から 0.7.3 でした。手順の問題なので、
今後はテキスト化を最後に行うようにします。

## v0.7.5 メインスレッド負荷の削減と例外保護

### 🔴 同じイベント列を3回走査していた

対象アプリを開いた瞬間、`currentStats()` は
`getCurrentSessionMinutes()` / `getTodayForegroundMinutes()` /
`getTodayLaunchCount()` の3つを呼んでいました。

**この3つがそれぞれ `queryEvents` を呼び、同じイベント列を
頭から全件走査していました。**同じ仕事を3回していたことになります。

しかもこれは、アクセシビリティサービスから
「アプリを開いたまさにその瞬間」にメインスレッドで走ります。
利用履歴が溜まった端末ほど重くなり、オーバーレイの表示が遅れます。

**修正**: `UsageTracker.getStats()` を追加し、
1回の走査で3つとも算出するようにしました。

従来の3メソッドと結果が一致することは、
4パターンのイベント列でシミュレーション検証済みです
（通常利用 / 短い往復あり / 現在も使用中 / イベントなし）。

### 🔴 起動の瞬間にキャッシュを丸ごと捨てていた

`statsCache.remove(packageName)` で、アプリを開いた瞬間に
キャッシュを破棄し、直後に全再計算していました。
一番重い処理を、一番待たせたくないタイミングで走らせていたことになります。

**修正**: 変わった値だけを差し替えるようにしました。
新しい起動なのでセッションは0、起動回数は自前カウントの値。
今日の合計使用時間はキャッシュの有効期間（数秒）では
ほとんど変わらないため、そのまま使います。

### 🔴 猶予期限と起動回数も毎回JSONパースしていた

`targetsCache` は導入済みでしたが、`KEY_GRACE` と
`KEY_LAUNCHES` は毎回パースしたままでした。
どちらも画面が切り替わるたびに読まれます。

**修正**: `readJson()` にキャッシュを持たせました。
書き込みは返した `JSONObject` をそのまま書き換えて保存するため、
キャッシュと実データがずれることはありません。

### 🟠 バックグラウンドからのサービス起動を保護

`SYSTEM_ALERT_WINDOW` を持っていればバックグラウンド起動制限は
免除されますが、ユーザーが設定から権限を外した直後などには
`ForegroundServiceStartNotAllowedException` が飛び得ます。

介入できないのは残念ですが、そのために
**端末で操作中のアプリごと落とすわけにはいきません。**
アラーム経由・アクセシビリティ経由の両方を try-catch で保護しました。

### 🟠 `hideKeyboard()` の保護

ビューがウィンドウから外れた直後に呼ばれると、
トークンが無効で例外になることがあります。
キーボードが閉じられなかっただけでアプリを落とす理由はないので保護しました。

### 🟡 カウントダウンの見え方

`CountDownTimer` の刻みはぴったり1秒ではないため、
最初の数字が一瞬で消えたり、最後の1秒が極端に短くなったりします。
「間を取る」ための画面としては落ち着かないので、
500ms 余分に持たせて吸収しました。

### 🟡 書き写し文の空文字対策

`target` が空だと「何も入力しなくても一致」になります。
現状 `Prefs` 側で空を弾いていますが、そこが変わっても
摩擦が消えないよう、検証側でも `isNotBlank()` を確認するようにしました。

## v0.7.6 キャッシュの適用範囲を揃えた

### 指摘：`recordResult` がキャッシュを経由していない

前回 `KEY_GRACE` と `KEY_LAUNCHES` にキャッシュを入れましたが、
統計の記録（`recordResult`）は毎回パースし直すままでした。
「オーバーレイを閉じたとき」しか呼ばれないため実害は小さいものの、
クラス内で扱いが揃っていないのは確かに気持ち悪い状態でした。

### 指摘されていないが、こちらの方が実害が大きかった箇所

同じ `KEY_STATS` を読む `getStatFor()` は、
**`getStreak()` から最大61回、`getRecentStats()` から7回**
呼ばれます。連続日数を1つ表示するだけで数十回のパースが走っていました。

メイン画面を開くたび、ウィジェットが更新されるたびに発生します。
`recordResult` より明らかに頻度が高いので、こちらも直しました。

### 「理由」の記録も取りこぼしていた

`KEY_REASONS` はJSON**配列**なので、オブジェクト用の
`readJson()` の対象外になっていました。
配列用の `readJsonArray()` を追加して揃えています。

件数を200件に切り詰める際は別インスタンスに差し替わるため、
キャッシュ側も新しい配列を指すよう更新しています。
ここを忘れると、切り詰め後に古い配列を参照し続けることになります。

### 検証

キャッシュした参照を書き換えてから保存する方式が、
「保存内容」と「キャッシュを捨てて読み直した結果」で
食い違わないことをシミュレーションで確認しました。
別インスタンスから交互に読み書きする状況も含めて一致しています。

これで `Prefs` 内の生の `getString` は、
パース関数の内部・単純な文字列取得・キャッシュ生成部の
3種類だけになりました。
