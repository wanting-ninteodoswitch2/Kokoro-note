# セキュリティ評価と今後の更新方針

## 1. このアプリの権限は「強い」という前提を持つ

まず正直に書いておくべきこととして、このアプリが要求する権限の組み合わせは、
**Androidマルウェアが典型的に使うものとほぼ同じ**です。

| 権限 | 悪用されるとできること |
|---|---|
| AccessibilityService | 画面内容の読み取り、操作の自動実行、入力の傍受 |
| SYSTEM_ALERT_WINDOW | 他アプリの上に偽画面を重ねる（タップジャッキング） |
| PACKAGE_USAGE_STATS | いつ何のアプリを使ったかの完全な行動履歴 |
| QUERY_ALL_PACKAGES | インストール済みアプリの全リスト（趣味・信条の推定材料） |

これらは「機能上必要だから」持っているものですが、
**必要だから安全、ということにはなりません。**
重要なのは、持っている権限に対して実装が何をしているかです。

## 2. 現状の評価

### 安全側に働いている設計

**インターネット権限を持っていない（最大の安全弁）**

`INTERNET` 権限を宣言しておらず、通信を行うコードも存在しません。
つまり、仮に何を記録したとしても、**それを外部へ送信する手段が
物理的に存在しません**。これがこのアプリの安全性の土台です。

セキュリティは「信用してください」より「そもそもできない」の方が
はるかに強い保証になります。

**画面の中身を読んでいない**

```xml
android:canRetrieveWindowContent="false"
android:accessibilityEventTypes="typeWindowStateChanged"
```

アクセシビリティサービスの設定で、画面内容の取得を明示的に無効化しています。
取得しているのは「いまどのパッケージが前面に来たか」という
パッケージ名のみで、パスワード欄やメッセージ本文は一切見えません。

権限として「読める立場」にはありますが、**設定で読めなくしてある**
という点が重要です。

**ログを出力していない**

`Log.d` や `printStackTrace` を一切使っていません。
Androidでは他アプリのログは通常読めませんが、
開発者モードやバグレポート経由で漏れる経路があるため、
そもそも出さないのが確実です。

**データは端末内のSharedPreferencesのみ**

外部ストレージ（他アプリから読める領域）には何も書いていません。
アプリ専用領域なので、root化されていない端末では他アプリから読めません。

### v0.6.3 で修正した点

**バックアップを無効化**

`allowBackup="true"` のままだと、保存データがGoogleのクラウドバックアップに
同期され、`adb backup` でも取り出せる状態でした。

このアプリは「開いた理由」としてユーザーが入力した文章を保存します。
これは**何に依存しているか、どんな気分のときに手が伸びるか**が
読み取れてしまう、かなり私的な記録です。

`allowBackup="false"` と `data_extraction_rules.xml` で、
クラウドバックアップ・端末間転送の両方から除外しました。

## 3. 残っているリスクと、その性質

### リスクA：サイドロード配布そのもの

自分でビルドして自分の端末に入れる限り、供給経路のリスクはありません。
**ただし、他人に配る場合は話が別です。**

APKファイルを誰かに渡す場合、受け取った側には
「そのAPKが本当にあなたのビルドしたものか」を検証する手段がありません。
アクセシビリティ権限を要求するAPKを配布するのは、
たとえ善意でも、受け取る側にとってはリスクの高い行為です。

**推奨**: 配布する予定があるなら、GitHubでソースを公開し、
「自分でビルドしてください」とする方が誠実です。

### リスクB：署名鍵の管理

リリースビルドに使う keystore ファイルを紛失すると、
**同じアプリとして更新できなくなります**（アンインストールして
入れ直すしかなくなり、データも消えます）。

逆に keystore が流出すると、第三者があなたのアプリを装った
偽の更新版を作れてしまいます。

**推奨**: keystore とそのパスワードは、パスワードマネージャなど
安全な場所にバックアップしてください。Gitリポジトリには絶対に入れない。

```
# .gitignore に必ず追加
*.jks
*.keystore
keystore.properties
local.properties
```

### リスクC：将来の自分による機能追加

いま安全なのは「通信しない」「画面を読まない」という制約を
守っているからです。将来、

- 「統計をクラウドに同期したい」→ INTERNET権限が必要になる
- 「アプリ内の特定画面だけ検知したい」→ 画面内容の読み取りが必要になる

といった要求が出たとき、この制約を崩すと安全性の土台が変わります。

**推奨**: そういう機能を足すときは、
「本当にその機能が必要か」を一度立ち止まって考えてください。
特に画面内容の読み取りは、一度有効にすると
パスワード欄まで見える立場になります。

### リスクD：端末が他人に渡る場合

「開いた理由」の記録は、端末のロックが破られれば読めます。
アプリ自体にパスコードはありません。

気になる場合は、記録機能をオフにする（摩擦を「なし」か「長押し」にする）
という選択肢があります。

## 4. 今後の更新方針

### 4.1 いま優先すべきこと

**まずビルドして実機で動かす。これが最優先です。**

現時点でこのコードは一度もコンパイルされていません。
5回のAIレビューを経ていますが、レビューで見つかるのは
「読めば分かる問題」だけです。

実機でしか分からないことが、まだ大量に残っています。

| 確認項目 | 見るべきこと |
|---|---|
| オーバーレイの表示 | チラつかずに被さるか |
| キーボード入力 | 理由入力・書き写しで文字が打てるか（機種差が出やすい） |
| 戻るキー | 閉じられるか |
| 長時間セッション | 30分以上使い続けて介入が来るか |
| 複数アプリ | 2つ以上を対象にして取り違えないか |
| 数時間後 | 電池最適化を切っても検知が止まらないか |
| ウィジェット | 一覧に出るか、数字が更新されるか |

### 4.2 バージョン管理を始める

いまは zip でやり取りしていますが、変更履歴が追えなくなります。

**推奨**: Gitリポジトリにする（GitHubのプライベートリポジトリで十分）。

```bash
cd maguard
git init
git add .
git commit -m "v0.6.3: 初期実装"
```

これで「動いていた時点」に戻れるようになります。
実機テストで壊れたとき、原因の切り分けが劇的に楽になります。

### 4.3 更新の進め方

**小さく変えて、都度実機で確認する。**

これまでは私が一度に大量の変更を入れてきましたが、
ビルドできる環境が整ったら、進め方を変えた方がいいです。

```
1つ機能を足す → ビルド → 実機で確認 → コミット
```

一度に複数変えると、壊れたときにどれが原因か分かりません。

**テストを先に更新する習慣**

`SessionLogicTest.kt` があります。ロジックを変えるときは、
まずテストに期待する動作を書いてから実装すると、
今回のような「直したつもりで直っていない」を防げます。

実際、v0.6.2 の修正では、指摘された箇所を直しただけでは
問題が解決していませんでした（救済役の関数自体に別の穴があった）。
テストがあれば、こういう見落としが機械的に検出できます。

### 4.4 OSバージョン追随

Androidは毎年、バックグラウンド実行とオーバーレイの制限を強化しています。
このアプリはその両方に依存しているので、影響を受けやすい部類です。

**特に注意が必要な変更**

- **Android 15以降**: バックグラウンドからのフォアグラウンドサービス起動条件が
  さらに厳格化。`SYSTEM_ALERT_WINDOW` による例外も、
  targetSdk 35 以降では「現在表示中のオーバーレイ」が必要になる可能性
- **アクセシビリティサービスの用途制限**: Googleは繰り返し
  アクセシビリティ権限の用途を絞る方向に動いています

**推奨**: `targetSdk` を上げるのは、**必要になるまで急がない**。
サイドロードで自分だけが使う分には、targetSdk 34 のままで動きます。
上げるときは、上記の項目を重点的に実機で確認してください。

### 4.5 Google Play への公開を考える場合

現時点では推奨しませんが、もし考えるなら以下が必要になります。

| 項目 | 内容 |
|---|---|
| アクセシビリティの用途申告 | 何のために使うかの説明と、審査 |
| QUERY_ALL_PACKAGES の申告 | 全アプリ一覧が必要な理由の説明 |
| プライバシーポリシー | 必須。「データを収集しない」旨を明記 |
| データセーフティ申告 | 収集項目の申告（このアプリは「収集なし」） |

アクセシビリティ権限を使うアプリの審査は厳しく、
説明が不十分だと公開停止になる例があります。
**まず自分で数ヶ月使って、本当に有用か確かめてからで十分です。**

---

## 5. まとめ

**現状のセキュリティ評価: 良好**

強い権限を持っていますが、

- 通信手段を持たない（データが外に出る経路がない）
- 画面内容を読まない設定にしてある
- ログを出さない
- バックアップを無効化した（v0.6.3）

という設計で、リスクを構造的に抑えられています。
「強い権限を持っているが、できることを自分で制限している」状態です。

**今後の要点**

1. まず実機で動かす（レビューで分かることは出尽くしている）
2. Git でバージョン管理を始める
3. 小さく変えて都度確認する
4. 通信機能と画面内容の読み取りは、足すときによく考える
5. targetSdk は必要になるまで上げない
